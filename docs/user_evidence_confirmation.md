# 任务级用户核实信息

工作台可以将用户明确核实的事实或对应关系作为独立任务输入交给 Core。该输入独立于网页正文和模型 proposal；`Fact.kind` 不提供模型可填写的用户确认状态，模型自报 `USER_CONFIRMED` 无效。

JSON facade 正常生成会保存 `execution_snapshot` 和 `confirmation_context`。前者包含 proposal、候选原文、输入问题、核验 checks/verdicts 和资料文件 SHA-256，属于调用方的私有执行数据；后者提供确定性的事项键、对象键、具体命题、输入、原文引用和行与目标的映射。缺少条件匹配候选时，可以从既有对象和明确用户条件建立值为空的候选，等待用户提供实际值与对应关系。空候选不会自行通过核验。

确认重算请求使用 `operation: "confirm"` 与已保存的 `execution_snapshot`；用户记录通过单独的 `--user-evidence` 调用方文件提供。调用方必须先验证任务、成果版本、事项键、对象、资料版本、指纹与适用条件，并控制该文件的写入。不得将这两个私有输入直接映射成任意 HTTP JSON 或模型附加字段。记录含 `confirmation_id`、`target_key`、`object_key`、`provenance: "user"`、明确的 `value`/`unit`、`status`；关系另绑定显式展示的输入值。该 CLI 边界面向受信的本机调用方，不是账户权限系统。

Core 再检查来源文件指纹、目标唯一性、对象对应、值与单位以及关系输入。合法用户补充不再要求原网页逐字证明新值，也不会再调用本地模型裁决该用户输入。已有核验只在完整检查输入未变化时复用。补充一条事实不会隐式确认相关关系；确认关系后仍需其余前提有效才执行原 Decimal 计算与状态传播。固有假设输入保持条件性；明确核实对应关系可以解除该关系自身的假设状态。

核实数值条件时，还需明确实际值与要求之间的比较方向（相等、不小于、不大于等），不会把最低数量要求自动当成相等条件。包含派生输入的关系会先重算其输入；输入值变化时，过期的下游核实标为待复核，独立有效部分继续交付。

用户更正采用新值，同时保留原候选值、原文与来源。与同一对象、属性、范围及单位的独立事实冲突时标为冲突。撤销重算从原 proposal 与原核验开始，仅影响其依赖结果；旧成果由调用方保留。投影区分“用户已确认”“依据用户确认”与网页原文依据，不直接设置选择状态。

对象与事项键使用对象名称、来源路径与内容指纹、引用片段、属性、范围及输入结构生成，不依赖临时节点 ID 或表格行号。仅节点 ID 变化不会丢失身份；对象名称、来源内容、引用或结构变化时采取保守策略，由调用方要求复核。该机制不进行语义实体合并；同名同范围无法唯一绑定时不给出自动确认目标。

范围边界由调用方明确记录。工作台默认限定于当前业务条件，用户可明确将某个事实限定为同一对象与规格的固有属性；关系始终受当前业务条件及实际输入值约束。新网页版本不自动继承旧记录。缺少派生候选时，确认不会凭空创建新的业务计算；自动补齐只针对已有明确用户条件的逐项匹配，并受 proposal 容量限制。

公开合同位于 `public_tests/state/test_user_evidence_contract.py`，使用商品包装与价格、合同费用与周期、设备型号与属性等合成资料。正常确认重算为零远程生成、零本地核验；首次为旧成果补齐结构可能需要一次原有生成流程。
